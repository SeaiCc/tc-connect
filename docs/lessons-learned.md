# 经验库 (Lessons Learned)

记录项目开发过程中发现的通用性问题和解决方案，供后续迭代参考。

---

## 2026-06-04: 会话管理器 (Task 1.3)

### 1. 后台守护进程的竞态条件防护

**问题**：后台清理守护进程 (`cleanupWorker`) 在检查 `s.cleanup` 是否为 nil 时未加锁，而 `Shutdown()` 同时在修改该字段，导致读写竞态条件。

**解决**：在守护进程启动时，立即将 `s.cleanup` 保存到局部变量，并在后续循环中使用该局部变量，而不是反复访问共享字段。

**通用经验**：后台守护进程（如定时任务、心跳检查、垃圾回收等）在访问共享字段时应使用锁保护，或在启动时立即保存引用到局部变量以避免与 `Shutdown()` 的竞态条件。守护进程退出路径应使用 `context.Context` 而非直接检查字段，确保取消操作的原子性。

---

### 2. 外部命令输出解析的顺序

**问题**：`parseSessionID` 函数在解析 `opencode session list` 输出时，正则表达式误匹配了 JSON 数组格式 `"[\"ses_abc\"]"` 中的 `ses_abc`。

**解决**：在尝试正则匹配前，先排除结构化数据格式（JSON 数组和对象），确保只处理纯文本格式的会话 ID。

**通用经验**：解析外部命令或 API 输出时，应首先排除结构化数据格式（如 JSON、XML），然后再尝试匹配目标模式，避免误解析。正则表达式匹配应作为最后手段，优先使用明确的条件判断排除已知错误格式。

---

### 3. 依赖外部 CLI 的工具方法测试策略

**问题**：`fetchSessionIDFromOpencode` 依赖 `opencode` CLI，测试环境中无法验证真实执行，且缺少对命令不存在、输出格式错误等边界情况的处理验证。

**解决**：
- 通过设置不存在的 `cliPath` 来测试错误处理路径
- 使用私有方法测试（通过公共 API 间接调用）
- 添加并发安全测试验证读写锁的正确性

**通用经验**：依赖外部 CLI 或第三方服务的工具方法，单元测试应重点验证错误处理路径（如命令不存在、超时、输出格式错误），而非成功路径。集成测试应单独编写，并考虑使用 mock 或容器化测试环境。

---

### 4. 会话 ID 生命周期管理

**问题**：临时会话 ID (`tmp_xxx`) 在执行后需要更新为真实会话 ID (`ses_xxx`)，但更新过程中可能出现重复、丢失等问题。

**解决**：使用 `UpdateSessionID` 方法原子性地删除旧 ID 并创建新 ID，确保会话数据的完整性。

**通用经验**：会话或资源 ID 的生命周期转换（如临时→永久、草稿→发布）应设计为原子操作，避免中间状态导致的数据不一致。旧 ID 的删除应在新 ID 创建成功后进行，确保可追溯性。

## 2026-06-04: 协议解析器 (Task 1.1)

### 1. 协议格式验证的完整性

**问题**：协议解析器需要验证 `[AGENT_NAME]||[PARAMS]||[SESSION_ID]` 格式，但缺少对特殊值（如 `END`）的处理。

**解决**：添加 `IsEndToken` 函数专门处理 `END` 标识，并在 `ParseProtocol` 中调用。

**通用经验**：协议解析应区分"语法正确"和"语义正确"。语法验证检查格式，语义验证检查内容有效性（如特殊标识、枚举值范围）。两者应分层处理，便于维护和扩展。

## 2026-06-04: 调度引擎 (Task 1.2)

### 1. 调度队列的并发安全

**问题**：调度队列在多线程环境下可能出现数据竞争。

**解决**：使用 `sync.Mutex` 保护队列操作，确保线程安全。

**通用经验**：共享数据结构（队列、栈、映射）在并发环境下必须使用锁或无锁数据结构（如 `chan`、`sync/atomic`）保护。Go 语言的 `race` 检测器是发现此类问题的有效工具。

## 2026-06-04: 并发控制 (Task 2.3)

### 1. 双重并发限制的资源隔离模式

**问题**：需要同时限制全局并发数和每项目并发数，但初始实现缺少项目级配置的灵活性，且项目池创建存在竞态条件。

**解决**：
- 使用两级信号量：全局信号量 + 每项目独立信号量池
- 项目池在首次访问时动态创建，创建过程由写锁保护防止重复创建
- 配置分离：`MaxConcurrent`（全局）和 `MaxPerProject`（项目级）独立配置

**通用经验**：多租户或资源隔离场景应使用"全局 + 分组"双重限制模式。全局限制防止系统过载，分组限制防止单个租户/项目耗尽资源。动态创建资源池时，必须持有锁完成"检查 - 创建"整个流程，或使用 `sync.Once` 确保单例创建。

---

### 2. 许可获取的异常安全（Exception Safety）

**问题**：获取并发许可后，若后续操作 panic，许可无法释放导致泄漏。

**解决**：使用 `defer` 在 `Acquire` 后立即注册 `Release`，而非使用手动标志变量。

**通用经验**：资源获取（锁、连接、文件句柄、并发许可）应遵循"获取即注册释放"原则，使用 `defer` 确保异常路径也能释放。手动标志变量（如 `needRelease`）容易在早期 return 或 panic 时遗漏，而 `defer` 由运行时保证执行。

---

### 3. 并发统计信息的原子性读取

**问题**：`GetActiveCount()` 返回的统计字段 `activeGlobal` 与信号量获取不同步。统计字段在获取两个信号量后才更新，导致在并发测试中（10 个 goroutine 竞争 3 个许可），偶发读取到超过限制的活跃数（如 4）。

**解决**：改用 `len(globalSemaphore)` 返回活跃数，而非统计字段。通道长度是原子操作，且与信号量状态严格一致（每次 acquire 向通道发送，每次 release 从通道接收）。

**通用经验**：并发控制器的状态查询应直接反映底层同步原语（如通道、锁）的状态，而非维护单独的统计字段。统计字段用于事后分析（如日志、监控），实时状态查询应使用原语本身（如 `len(channel)`、`atomic.Load`）。若必须维护统计字段，需确保更新与信号量操作原子化，或在获取信号量前就更新统计（失败时回滚）。

**补充**：`sync.RWMutex` 适用于读多写少的场景（如监控指标），但在高并发写入场景下，直接使用无锁操作（如 `len(channel)`）性能更优。

---

### 4. 边界条件的防御性编程

**问题**：缺少对空字符串项目名、零值配置、大量项目名等边界情况的处理。

**解决**：
- 空项目名映射为 `"default"`
- 零值配置使用合理默认值（5, 2）
- 支持 `Cleanup` 清理长时间未使用的项目池防止内存泄漏
- 添加边界测试用例（100+ 项目名循环）

**通用经验**：并发控制器的输入参数（项目名、配置值）应做防御性处理：空值映射默认、零值使用合理默认、支持资源清理。边界测试应覆盖极端值（0, 1, 极大值）和大量并发场景，确保内存可控。
